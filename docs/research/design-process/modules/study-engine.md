# Module record: study engine (participant journey)

Engineering location: `src/server/study/` (engine, allocation, answers, config, instruments,
tokens, request helpers, server actions), `src/components/study/`, participant pages under
`src/app/(study)/study/`. Tests: `tests/unit/study/` (3 files, 18 tests),
`tests/integration/study-engine.test.ts` (11 tests), `tests/e2e/study-journey.spec.ts`
(5 tests). Every number below cites the file that defines it or the test that checks it.

## Requirements implemented

- Procedure, concept note §8, P94 (CN-14): "All participants complete a short prior-knowledge
  test, the assigned learning/exploration task, an immediate post-test, a relational
  reconstruction task, and a short UX/cognitive-load questionnaire."
- Design, §8, P94 (CN-13): "A simple between-group design can allocate approximately 20
  participants to each pathway." The within-participant alternative is "To be decided later"
  (§8, P95).
- Secondary outcomes, §9, P101–P105 (CN-17): pre/post questions, a transfer "why?" problem, a
  "short validated perceived-load measure", and UX "a short measure such as SUS, UMUX-Lite or
  UEQ-S."
- Lead requirements: pseudonymous participation, versioned consent, withdrawal without silent
  deletion, auditable randomisation, condition locked into the signed session, both conditions
  moving on identically when the shared learning budget ends.

## What is measured and recorded

- Per participant: pseudonymous code, stratum (if any), status, consent decisions with version
  and text hash, withdrawal time and fixed reason.
- Per allocation: algorithm, seed, sequence index, block index, stratum, protocol version,
  time; reassignment as a separate `manual` allocation with its reason.
- Per session: condition, device covariates and check verdict, learning start/end (server),
  interruptions, assessment versions presented, status and end time.
- Per item: raw answer or skip, presentation and answer times, client time, duration;
  objective item scores and per-assessment totals as derived scores.

## Implications for the paper

- Report the allocation as seeded permuted blocks (block size and seed from the config), with
  the allocation records allowing independent recomputation.
- Report the procedure order actually configured (S2) and that steps could not be skipped or
  repeated.
- Allocation follows the pre-test (S19), so the pre-test and pre-map are taken blind to
  condition; report the stratification source and cutoff (S21), and that allocation is refused,
  never altered, when the stratum score is missing.
- The load, sickness and presence ratings are taken immediately after learning (S20); presence is
  analysed within the 3D group only (S22).
- Cognitive-load items are reworded with one neutral term identical in both conditions (S24);
  report this and the reliability from our own data (D7 risks).
- Device-check exclusion or reassignment can only affect the immersive arm (S3). With
  `exclude` this is condition-dependent attrition; with `reassign` reassigned participants are
  not randomised and should be analysed separately or excluded (per-protocol vs
  intention-to-treat must be stated).
- The learning budget starts at the same procedural moment in both conditions (S11); report the
  immersive loading time as part of the budget.
- Questionnaire instruments are not yet selected; no validated instrument is presented until
  the researchers add the wording with its citation (S14).
- Repeat participation is detected per browser only (S17); state this limitation.

  `design = within` explicitly.
- The familiarisation pages `/learn/2d/practice` and `/learn/immersive/practice` (S23).
- Verified endpoint labels for the 5-point presence scale and the 7-point UMUX-LITE, and labels
  for the middle SSQ points (S29–S32).
- The bootstrap demo study `demo-review-walkthrough` cannot be run through the engine: it is
  pinned to the review snapshot, which can never be published, so it can never be activated.
