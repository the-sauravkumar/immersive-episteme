# Module record: research console, parity engine, derived metrics, exports and analysis

Implements DR-015 (content, exposure and citation equivalence; navigation timed separately from
outcomes) as an executable activation guard, the concept note's analytics requirement CN-20,
and the research-data export and analysis path. Engineering reference: the source files named
below. Every number cites the test, command or file that produced it.

## Requirements served

- Concept note §10, P139 (verified in `docs/research/technical-requirements.json`, CN-20):
  "Derived indicators may include path length, exploration breadth, exploration depth, revisit
  rate, cross-domain transitions, science-layer engagement, path entropy and sequence patterns."
  and "A particularly interesting analysis would compare a participant's navigation structure
  with the concept map produced after learning."
- Master prompt (`D:/Work/IIT-KGP/Prompt/Master_Prompt.md`) §11: "Establish a content-parity
  mechanism or validation report to check equivalent content exposure." §10.3: "Do not equate
  frequent interaction, longer dwell time, or more visited exhibits with better learning without
  supporting evidence." §10.4: "Include a way to verify that exported records can be joined by
  participant, session, condition, concept, and event identifiers."
- DR-015 (`../decisions.md`): equal content, equal exposure, equal citation availability;
  navigation timings never in outcome data.

## Decisions

### R1. Parity is a machine-readable report, and activation depends on it

- **Context.** "Experimental equivalence must be implemented, not assumed" (master prompt §11
  heading). The database already refused activation without a published snapshot and manifest
  (migration 0005) but knew nothing about content, citation, prompt or exposure equivalence.
- **Options.** (a) a checklist page for researchers to tick; (b) a database trigger;
  (c) a pure report generator in the application, stored append-only, required at activation.
- **Decision.** (c). `runParityChecks` (`src/server/research/parity/engine.ts`, generator
  `parity/1.0.0`) is pure and deterministic; `activateStudy` (`src/server/research/studies.ts`)
  generates a fresh report inside the activation transaction, stores it in `parity_reports`
  (append-only, `report_sha256` generated by the database) and activates only if no critical
  check failed and the study inputs it judged (`inputSha256`, a canonical hash of protocol
  version, design, config, conditions, battery and pins) are unchanged. A refused activation
  keeps its report as evidence. (a) was rejected because it is not verifiable; (b) because the
  checks need the compiler's scope rule and text analysis, which belong in TypeScript.
- **Evidence.** `tests/unit/research/parity-engine.test.ts` (11 tests) and
  `tests/integration/research-console.test.ts` ("refuses activation while the parity report
  fails, and keeps the report"; "activates once the parity report passes").

### R2. What "the same content" means operationally

- **The study content set** (what "reachable in 2D" means) is the spatial compiler's scope rule
  `selectScope` applied to the study's traditions: every concept of a selected tradition, shared
  concepts linked to them (transitively over shared concepts), and comparison concepts spanning
  at least `minTraditions` selected traditions (read from the pinned rule set, default 2). The 2D
  module implements the same rule independently (`src/features/learning-2d/scope.ts`, constant
  `MIN_COMPARE_TRADITIONS = 2`); the parity check compares the manifest against this set, so a
  divergence between the conditions' content selection would show as missing or extra exhibits.
- **Checks** (critical unless stated): base (published release snapshot; manifest compiled from
  it for exactly the study's traditions, validated and published; valid config with both
  interfaces); (a) every manifest concept and relationship id is in the snapshot, every
  explanation shown in 3D equals the snapshot explanation verbatim, media per concept are equal,
  comparison sets are equal, claim totals are equal; (b) no concept of the set lacks an exhibit
  and no exhibit is outside the set (unencoded relationships are a warning: the 3D panel must list
  them as the 2D page does); (c) the claim-to-source citation pairs and the cited sources are
  identical; (d) no condition overrides exposure, guidance, prompts, assessments, search or
  traditions, condition configs are identical, every battery assessment is locked (battery
  completeness and guidance cues are warnings for researcher review); (e) exposure is
  `fixed_time` with minutes, not overridden per condition, and every learning budget already
  stamped on a session equals it; (f) no condition-specific extra text.
- **Rejected.** Comparing rendered 2D pages with the 3D scene (needs a browser per check and is
  brittle); comparing only counts (would miss a swapped concept).

### R3. Detecting extra instructional text in 3D

- **Decision.** Every learner-visible string in the manifest (keys `label`, `text`,
  `explanation`, `title`, `caption`, `description`, `prompt`, `instruction(s)`, `body`,
  `summary`, `message`, `hint`, `tooltip`, `narration`, `announce`; never inside `trace`,
  `rationale` or `encodes`, which are research documentation) must decompose, case-insensitively
  and on whole words only, into snapshot strings (concept titles, summaries, local terms, claims,
  relationship explanations and conditions, tradition names, category and relationship-type
  labels), the rule set's way-finding labels, three fixed room names of the compiler layout
  ("Comparison hall", "Entrance lobby", "Entrance"), numbers, and a closed lexicon of 20 interface
  words taken from the compiler's label templates (`CHROME_LEXICON`: inspect, entering,
  entrance, why, it, leads, to, explains, part, of, includes, related, before, sequence, stages,
  start, compare, compared, with, and). Any other word fails the check.
- **Tried and revised.** The first version matched phrases as raw substrings and case-sensitively.
  On the real manifest it reported 335 false positives: short local terms split words
  ("Compare with" left "com, re") and relationship-type labels are lower case in the snapshot but
  capitalised in hotspot labels. Whole-word, case-insensitive matching plus the template lexicon
  and the room names reduced this to 0 (command output of the probe run against the development
  database; see R7).
- **Paper implication.** Hotspot verbs such as "Why it leads to" and "Explains" are 3D interface
  wording for relationship types whose 2D wording is the snapshot label (e.g. "causes"). They name
  a link; they do not add craft knowledge. This is a judgement the researchers should confirm.
- **Limitation.** The 2D condition has no compiled artefact to scan; its text discipline rests on
  the 2D pages rendering only read-model strings.

### R4. Navigation metrics v1 (CN-20) and their unit of analysis

- **Decision.** One condition-neutral unit: the *visit*, i.e. a content-exposure interval
  (`exposure_started`), which both conditions emit through the shared time accountant (2D: concept
  content at least 50% in view; 3D: information panel open). Consecutive exposures of the same
  concept collapse into one visit. Definitions in `src/server/research/metrics/navigation.ts`:
  path length (visits), breadth (distinct concepts; traditions and categories in details), depth
  (mean distinct layers per visited concept), revisit rate ((visits - distinct)/visits),
  cross-domain transitions (consecutive visits in different traditions; shared concepts form the
  domain "shared"; cross-category count in details), science-layer engagement (science exposure
  ms / all exposure ms), path entropy (conditional entropy H(next | current) of first-order
  transitions, in bits; the visit-distribution entropy in details), sequence patterns (distinct
  bigrams of the analytic-concept sequence, top bigrams and trigrams in details) and relationships
  followed. Null, never a guess, when undefined.
- **Rejected.** Room/page entries as the unit (3D rooms hold many concepts, 2D pages one: not
  comparable); `exhibit_selected` vs `content_item_selected` (different raw affordances).
- **Path entropy** is marked provisional: the master prompt asks for it only "where an appropriate
  definition is established" (§10.3). The conditional form measures route predictability; the
  researchers may prefer the visit-distribution form, which is also stored.
- **Evidence.** `tests/unit/research/derived-metrics.test.ts` (6 tests) checks every value on a
  hand-computed event stream (e.g. revisit rate 0.4, depth 4/3, conditional entropy 0 for a
  deterministic route and 0.5 bits for a two-way branch).

### R5. Navigation-to-concept-map correspondence

- **Decision.** `nav.map_correspondence` v1 (`metrics/correspondence.ts`): value = Jaccard index
  between the undirected concept pairs navigated (consecutive visits and followed relationships)
  and the pairs of the final post-learning map; details count concepts exposed, concepts
  inspected (completed exposure with active time), relationships followed, and map links that
  match or do not match a snapshot relationship (direction and type respected when given),
  cross-tabulated with following and inspection.
- **Why the snapshot graph and not the reference map.** Outcome scoring against the adjudicated
  expert reference map belongs to the assessment pipeline (`derived_scores`). This measure is a
  descriptive structural comparison, kept in `derived_metrics` so it cannot be mistaken for an
  outcome.

### R6. Derived metrics are versioned, recomputable and kept apart from outcomes

- All behavioural metrics (6 timing metrics from `src/features/telemetry/metrics.ts`, 9 navigation
  metrics, 1 correspondence metric: 16 definitions in `METRIC_DEFINITIONS`) are written only to
  `derived_metrics` with `input_sha256` over the ordered (event_id, seq) list plus the concept
  map's id and revision, and pipeline `research-metrics/1`. Recomputation is idempotent (second
  run writes 0 rows; integration test) and stale rows are detectable. The database refuses
  timing names in `derived_scores` (integration test asserts the refusal).
- Every analytics view carries an observational notice and states its filter (excluded,
  withdrawn and non-experimental sessions are set aside, never deleted).

### R7. Findings on the real development data

A parity report for the development study `demo-review-walkthrough` (review snapshot of the six
traditions' content, combined manifest of ajrakh, machilipatnam-kalamkari and sanganeri) gave:
content set 254 concepts (12 comparisons), 421 relationships, 727 claims citing 79 sources;
coverage, claims, comparisons, explanations, citations (796 claim-source pairs in each condition)
and the text check pass; 4 critical failures: the snapshot is a review snapshot and draft (by
design never activatable), the manifest is `valid` not `published`, exposure is self-paced, and
**15 exhibits show an image (16 image references in the manifest) that the snapshot does not
give the 2D condition** (`a.media`). The last is a real parity gap: the manifest freezes
`media_candidates` images whose licences are not reviewed, while the snapshot's `assetIds` are
empty (documented in `docs/architecture/data-and-telemetry-layer.md` §3). Either both conditions
show those images (after licence review, through snapshot assets) or neither does. Source: the
stored parity report in the development database (`parity_reports`, generator `parity/1.0.0`).

### R8. Exports: one self-describing bundle, two scopes, verifiable offline

- **Decision.** `buildExportBundle` (`src/server/research/exports/build.ts`) produces one JSON
  bundle (format `immersive-episteme-research-export`, schema 1) with 11 tables in the
  pseudonymised scope and 13 in the identified scope (`exports/dictionary.ts`), the study
  configuration snapshot and battery, content and manifest hashes (snapshot payload sha256,
  snapshot items, manifest hash, rule-set config sha256), the concept and relationship facts
  needed to rejoin and recompute, a data dictionary, reproducibility metadata (app build,
  pipeline and generator versions, metric definitions, event-type registry, PostgreSQL version,
  latest parity report) and per-table sha256 checksums over canonical JSON. Each table is also
  downloadable as RFC 4180 CSV.
- **Scopes.** Pseudonymised (`exports.create`: researchers and analysts): participants only as
  their study code; no consent records, no researcher free text (annotations, deviation
  descriptions, exclusion and withdrawal details: their categories only). Identified
  (`exports.identified`: principal investigator only) adds consent records, annotations and the
  free text. The scope is decided on the server from the caller's permissions
  (`exports/access.ts`); an analyst asking for identified data gets 403 (unit test; also checked
  against the running app). Participant-produced research data (responses, concept maps) is in
  both scopes.
- **Re-import validation.** `validateExportBundle` re-checks checksums, columns, unique keys and
  joins by participant, session, condition, concept, event and concept map, and recomputes every
  exported derived metric from the exported raw events (value and input hash must match). The
  integration test round-trips a bundle through JSON and every table through CSV, and shows that
  tampering (a moved event; a changed metric with a recomputed checksum) is detected. The Python
  package verifies the same checksums independently (`analysis/tests/fixtures/canonical.json`
  produced by the TypeScript canonicaliser; 2 real bundles downloaded from the running app
  validated with `python -m episteme_stats validate`).

### R9. Statistical analysis is exploratory and reproducible

- `analysis/episteme_stats` (numpy 2.5.4, scipy 1.18.1, pinned in `analysis/requirements.txt`):
  descriptives per condition; Welch's t with the CI of the mean difference, Hedges' g with an
  approximate and an exact (noncentral t) CI, Mann-Whitney U with rank-biserial correlation, and a
  seeded percentile bootstrap; baseline (pre-test) adjustment by ANCOVA with a
  homogeneity-of-slopes check; a missing-data report (complete-case, no imputation); and an
  a-priori power helper. Every report carries an "EXPLORATORY" notice until the researchers
  approve the analysis plan.
- The power reference in every report is the preregistered plan (study decision D4): a two-group
  ANCOVA at ρ = 0.6, 51 analysable per group (test `test_reproduces_the_d4_ancova_plan`: n = 51,
  29 and 17 per group for d = 0.45, 0.60 and 0.80; power 0.410 at 20 per group for d = 0.45;
  minimum detectable d 0.73 at 20 per group). The concept note's t-test at 20 per group is kept
  only as a labelled comparison and still reproduces `docs/research/technical-requirements.md`
  §4 exactly (test `test_reproduces_the_planned_sample_facts`: d = 0.45 gives 0.284, 79 per
  group for 80%). Until the final review (scoring-10) the report showed only the t-test plan.
- The analysis table has one row per participant, as on the dashboard (final review scoring-02,
  -03): a never-allocated session is counted as `unallocated`, not an error; after a WebGL
  reassignment the pre-test on the abandoned session is the baseline of the 2D row. Concept-map
  scores are read against the study's analysis reference map and the current metric version
  (`study.analysisReferenceMaps` and `reproducibility.scoringMetricVersions` in the bundle;
  scoring-04); a baseline and an outcome scored against different references are never paired.
- **Evidence.** `analysis/tests/test_episteme_stats.py`: 21 tests, all passing.

### R10. Study configuration and versioning

- A study is created as a draft with both conditions (2D and 3D, equal weight). Everything the
  protocol fixes lives in `studies.config` (traditions, allocation, exposure, guidance, search,
  mini-map, WebGL policy, retention, consent version, inclusion/exclusion criteria) and the
  battery in `study_assessments`; every save writes an append-only `audit_log` row with before
  and after state, which is the configuration history shown on the study page.
- Active and closed studies are frozen by the database; a protocol change is a new version
  (`newStudyVersion` clones conditions, battery, config and pins into a new draft with a new
  protocol version). Rejected: editing in place with a version counter (the database forbids it
  after activation, and allocations record the protocol version they were made under).

## Implications for the paper

- Report that activation of every study required a stored, hash-sealed parity report with no
  critical failure, and list the checks (R2). Report the parity report hash with the results.
- Report the operational definitions of the navigation metrics (R4) and correspondence (R5) as
  descriptive and exploratory; the visit unit is the same in both conditions.
- Report exposure and navigation time as covariates or descriptive variables (DR-015), never as
  outcomes.
- Data availability: the export bundle with checksums and data dictionary can be shared as the
  analysis dataset; its integrity can be checked offline.
